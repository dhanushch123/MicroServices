Spring Cloud Gateway filters, explained

What a filter is, what exchange and chain really contain (seen in the debugger), how to set the order, and where service discovery fits in.

1. Why: request, gateway, filters, service discovery

The client never talks to Order or Inventory directly. It talks to the gateway, and the gateway has to answer three questions before it can forward anything: which route is this?, what must happen to the request first?, and which actual machine runs that service? Filters sit exactly between the first and the last question.

Client: GET /api/v1/orders/123
Gateway receives the request (Netty, non-blocking)
Route matching: predicates such as Path=/api/v1/orders/** pick the routeThe route says uri: lb://ORDER-SERVICE and carries its own filters.
Filter chain = global filters + that route's filters, sorted by orderYour logging, StripPrefix=2, auth, rate limiting, etc. Pre-logic runs here, going down.
Load-balancer filter asks the discovery client (Eureka)lb://ORDER-SERVICE becomes a real host:port. This is itself a filter, so it only runs once the chain reaches it.
Routing filter sends the request to the chosen instance
Order Service replies, and the response travels back up the chain (post logic) to the client

Why filters come before service discovery: the filters decide whether the request is allowed through and what it looks like (path rewritten, headers added, rejected with 401, rate-limited). It would be wasteful, and wrong, to look up an instance and open a connection for a request that a filter is going to reject or change. So the order is: match route, run filters, resolve the service, forward. Discovery is simply one of the last filters in the chain.

Because the logging filter runs before the load-balancer filter, the URL it sees is still the gateway URL. The resolved instance only exists after the load-balancer filter has run.

2. This is not the Spring MVC you know

Spring MVC

Blocking. Normally one worker thread is held for the whole request, including the time spent waiting for a database or another service.

Gateway (WebFlux)

Reactive and non-blocking. A small number of event-loop threads start I/O and move on. When the response arrives, the pipeline continues.

Request 1 ─┐
Request 2 ─┤
Request 3 ─┤──→ small pool of event-loop threads
Request 4 ─┤      (start I/O, don't sit waiting)
Request 5 ─┘

A gateway spends nearly all its time waiting on the network (client to gateway to service and back), so this model lets a few threads serve thousands of connections.

Don't memorise "there is no thread per request". Threads still exist. The accurate statement: WebFlux uses few event-loop threads and non-blocking I/O instead of parking a thread while waiting. Consequence: never put blocking code (JDBC, Thread.sleep(), blocking HTTP) inside a filter, it blocks the event loop and hurts every request on that thread.

3. What is ServerWebExchange exchange?

The whole HTTP interaction currently passing through the gateway: the request and the response together (hence "exchange").

exchange
├── request   → method, URI/path, headers, query params
├── response  → status code, headers, body
└── attributes → a map of extra data shared between filters
exchange.getRequest().getMethod()   // GET
exchange.getRequest().getURI()      // http://localhost:8080/api/v1/orders/123
exchange.getRequest().getHeaders()
exchange.getResponse().getStatusCode()  // only meaningful after the response exists

What the debugger shows

4. What is GatewayFilterChain chain?

The remaining filters. Calling chain.filter(exchange) means: "my part is done, pass the exchange to the next filter."

Request → Logging → Auth → RateLimiter → LoadBalancer → Routing → Service
If you do not call chain.filter(exchange), the request stops there and never reaches the service. That is how a filter can reject a request (set a 401 on the response and return without continuing).

What the debugger shows

The chain is a DefaultGatewayFilterChain holding a filters list (size 12) and an index. The index is a cursor: each call to chain.filter() runs the filter at the cursor and moves it forward. Here index = 10 because the logging filter at position 9 is running and the next one is Netty routing.

This is the "request, gateway, filters, service discovery" idea made visible: your StripPrefix (4) runs before the load balancer (6), and the actual network call (10) is last. The list also proves that your global filter and the route's filter are merged into one chain.

5. What is Mono<Void>?

From Project Reactor. Mono<T> means "zero or one value of type T, delivered asynchronously". Mono<Void> means "this will finish, but carries no value". A filter doesn't return a user or an order; it only signals "processing is complete".

The filter does not run the rest of the request immediately. It returns a description of the remaining work (chain.filter(exchange)), and WebFlux subscribes to it and executes it without blocking a thread. Compare:

// blocking mindset (not what we do)
Response r = callService();   // thread waits
return r;

// reactive mindset
return chain.filter(exchange); // "here is the rest of the work; tell me when it completes"

6. Global filter: runs on every request

@Component
@Slf4j
public class GlobalLoggingFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        log.info("Global Logging Filter");              // PRE: before the service
        return chain.filter(exchange)
            .then(Mono.fromRunnable(() -> {              // POST: after the response
                log.info("Post filter: {}", exchange.getResponse().getStatusCode());
            }));
    }

    @Override
    public int getOrder() { return 5; }
}

Pre and post logic

PRE   code before chain.filter(exchange)      ← request is going down
         ... other filters, discovery, service ...
POST  code inside .then(...)                  ← response is coming back up

.then(Mono.fromRunnable(...)) runs only after the rest of the chain has completed, so now the response status exists and can be read. Post logic of several filters runs in reverse order (last filter in, first out), like unwinding a stack.

Code placed after the return line's expression is not "post logic"; only things attached with .then(...) (or similar operators) run later.

7. How to define the order of a filter

Implement Ordered and return a number from getOrder(). Lower number runs earlier. (@Order(5) on the class also works.)

Before: no order

In the first screenshot the logging filter was position 9, a plain GatewayFilterAdapter, not wrapped as an OrderedGatewayFilter like the others. A filter with no order is treated as the lowest priority, so it lands near the end, just before the routing filters. It runs after the load-balancer filter, which is rarely what you want for logging.

After: getOrder() = 5

FilterOrderSource
StripPrefix (first filter in YAML list)1Route filters get 1, 2, 3 ... by their position in the YAML list
GlobalLoggingFilter5Your getOrder()
RouteToRequestUrlFilter10000Built-in
ReactiveLoadBalancerClientFilter10150Built-in
NettyRoutingFilterInteger.MAX_VALUEBuilt-in, always last

Global and route filters are merged and sorted together by these numbers, which is why a global filter with order 5 slots in between route filters 1 and 2. Rule of thumb: use small numbers (or negative) for things that must happen early (logging, auth), and avoid going past 10000 unless you deliberately want to run after the target URL is built.

Order also controls the post phase in reverse. Order 5 means "early on the way in, late on the way out".

8. Route-specific filters (AbstractGatewayFilterFactory)

A global filter runs for every request. What if a filter should apply to one route only, for example extra logging just for the Order service? That is what a route-specific filter is for, and the way to build one is AbstractGatewayFilterFactory.

AbstractGatewayFilterFactory   (abstract base class from Spring Cloud Gateway)
          ↓ you extend it
Your custom filter factory     (CustomLoggingGatewayFilterFactory)
          ↓ it creates
A GatewayFilter                (the real filter)
          ↓ you attach it in YAML
One specific route

You write three things

WhatWherePurpose
1. The factory classJavaBuilds the filter. Extends AbstractGatewayFilterFactory<Config>
2. The Config classJava (nested inside the factory)Holds the values you pass from YAML
3. The YAML entryapplication.ymlAttaches the filter to a route and supplies the values

Step 1: the factory class

@Slf4j
@Component
public class CustomLoggingGatewayFilterFactory
        extends AbstractGatewayFilterFactory<CustomLoggingGatewayFilterFactory.Config> {

    public CustomLoggingGatewayFilterFactory() {
        super(Config.class);
    }
    ...
}
  • @Component: makes it a Spring bean, so Gateway can discover it by name.
  • extends AbstractGatewayFilterFactory<Config>: the abstract class does the plumbing (reading YAML, binding it to your config object). It leaves one method for you to implement: apply(Config).
  • super(Config.class): "for this filter factory, my configuration class is Config". Gateway needs to know the class so it can create a Config object and fill it from the YAML args. That is also why Config needs setters (@Setter) and getters (@Getter).

Step 2: implement apply(Config config)

Read it literally: given a Config, return a GatewayFilter.

@Override
public GatewayFilter apply(Config config) {

    return (exchange, chain) -> {

        // PRE: runs before the rest of the chain
        log.info("Custom logging filter applied");
        log.info("Custom logging filter pre processing: {}", config.getMessage());

        return chain.filter(exchange)
                .then(Mono.fromRunnable(() -> {
                    // POST: runs after the response comes back
                    log.info("Custom logging filter post processing: {}",
                             exchange.getRequest().getURI());
                }));
    };
}

GatewayFilter is an interface (public interface GatewayFilter extends ShortcutConfigurable), so you must supply an implementation. Its one method to implement is Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain). With a single method, you can write the implementation as a lambda (exchange, chain) -> { ... }. This is the same thing as:

return new GatewayFilter() {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        log.info("Custom logging filter applied");
        return chain.filter(exchange);
    }
};

Inside the lambda you work with the two things from sections 3 and 4: exchange (the request and response) and chain (continue the pipeline). You can log, read headers, modify the request, or stop the request. The config parameter is available inside the lambda because the lambda "captures" it.

Two different moments. apply(config) runs when the route is built (application start-up, once per route that uses the filter). The lambda inside it runs every time a request hits that route.

Step 3: the Config class

@Getter
@Setter
public static class Config {
    private String message;
}

It is just a data holder for the filter's settings. One field per argument you want to accept from YAML. It is a static nested class, so it exists without needing a factory object (the reason is explained in section 9). You use the value with config.getMessage().

    args:

So the suffix is a naming convention Gateway relies on: a class should end with GatewayFilterFactory, and that suffix is what gets removed to make the YAML name. Built-in filters follow the same pattern.

How Gateway finds your filter by name

At start-up Gateway collects every GatewayFilterFactory bean into a map. The key is the class's simple name with the text GatewayFilterFactory removed. When a route lists name: CustomLogging, Gateway looks that exact text up in the map. If nothing matches you get the error "Unable to find GatewayFilterFactory with name ...".

Class nameKey in the mapWrite in YAMLStatus
CustomLoggingGatewayFilterFactoryCustomLoggingCustomLoggingCorrect, recommended
CustomLoggingFilter (no suffix, but still a GatewayFilterFactory bean)CustomLoggingFilter (nothing to remove)CustomLoggingFilterRecognised, but not a supported convention and may be removed in future releases
CustomLoggingGatewayFilterFactoryCustomLoggingCustomLoggingGatewayFilterFactory (the full name)Not found, because the key has the suffix removed
Rule to remember: the name in YAML must equal the key, which is the class name minus GatewayFilterFactory. Name your class XyzGatewayFilterFactory and write Xyz. A class with no suffix (like CustomLoggingFilter) is simply referenced by its whole class name, but the Spring docs say not to rely on that, so use the suffix.

How YAML maps to Config

args:
  message: "Custom Logging Filter for Order Service"
   │
   └── key "message" is matched to the field name in Config
          ↓
Config.message = "Custom Logging Filter for Order Service"
          ↓

The key under args must match the field name in Config. If you add another field (for example private boolean logHeaders;) you pass it as another key under args.

Two ways to write a filter in YAML

Shortcut form

- StripPrefix=2

Compact. The value after = goes to the first field (parts). It works for built-ins because they declare their field order.

Full form

- name: CustomLogging
  args:
    message: "Hello"

Explicit name and args. Use this for your own filters, as in this project.

Optional: if you want - CustomLogging=Hello to work too, override shortcutFieldOrder() in your factory and return List.of("message"). That method comes from ShortcutConfigurable, which is why GatewayFilter extends it.

Putting it together

application.yml
   - name: CustomLogging
          │  (suffix removed from class name)
          ↓
CustomLoggingGatewayFilterFactory   ← found as a bean
          │  super(Config.class) says: bind YAML into Config
          ↓
Config { message = "..." }
          │
          ↓
apply(config)  → returns GatewayFilter       [start-up, once]
          │
          ↓
(exchange, chain) -> { ... }                  [every request to that route]

Different routes, different values: attach CustomLogging to the Order route with one message and to the Inventory route with another. It is the same factory class, but each route gets its own Config and its own GatewayFilter.

Where it runs in the chain

In the debugger the route filters appear in the chain with an order equal to their position in the YAML list, so StripPrefix=2 is order 1 and CustomLogging is order 2. They are merged with the global filters and sorted (see section 7).

Common mistakes

  • Forgetting @Component: Gateway reports an unknown filter name.
  • Writing the full class name (with GatewayFilterFactory) in YAML. Use the name without the suffix.
  • Class name not ending with GatewayFilterFactory.
  • No setters on Config, or an args key that doesn't match a field name. The value stays null.
  • Forgetting return chain.filter(exchange): the request never reaches the service.

Quick terminology

The factory (CustomLoggingGatewayFilterFactory) creates filters. The GatewayFilter is the actual filter that handles requests. Config holds the YAML values given to it.

9. Why is Config a static nested class?

Inner (non-static)

class Outer {
  class Inner {}
}
Outer o = new Outer();
Outer.Inner i = o.new Inner();

Tied to one Outer object and holds a hidden reference to it.

Static nested

class Outer {
  static class Inner {}
}
Outer.Inner i = new Outer.Inner();

No Outer object needed. Just grouped inside it by name.

Config is static because it doesn't need a reference to a particular factory instance, which also lets Gateway create it on its own while binding YAML. It is not static "because it is configuration"; that's a separate point.

10. Authentication and authorization in the gateway

Authentication asks "who are you?" (is the JWT valid?). Authorization asks "what may you do?" (roles, permissions). A failed authentication is 401 Unauthorized; being known but not allowed is 403 Forbidden. The gateway is a natural place for the first check, because a filter can reject a bad request before any service discovery or network call happens.

Corrected filter

@Component
public class AuthenticationGatewayFilterFactory
        extends AbstractGatewayFilterFactory<AuthenticationGatewayFilterFactory.Config> {

    private final JwtService jwtService;

    public AuthenticationGatewayFilterFactory(JwtService jwtService) {
        super(Config.class);
        this.jwtService = jwtService;
    }

    @Override
    public GatewayFilter apply(Config config) {
        return (exchange, chain) -> {
            if (!config.isEnabled()) return chain.filter(exchange);

            String authHeader = exchange.getRequest().getHeaders()
                    .getFirst(HttpHeaders.AUTHORIZATION);
            if (authHeader == null || !authHeader.startsWith("Bearer ")) {
                return unauthorized(exchange);
            }

            try {
                Claims claims = jwtService.getClaimsFromToken(authHeader.substring(7).trim());
                Long userId = jwtService.getUserId(claims);
                List<String> roles = jwtService.getUserRoles(claims);

                // build() returns a NEW request: it must be passed on
                ServerHttpRequest request = exchange.getRequest().mutate()
                        .header("X-User-Id", userId.toString())
                        .header("X-User-Roles", String.join(",", roles == null ? List.of() : roles))
                        .build();

                return chain.filter(exchange.mutate().request(request).build());
            } catch (JwtException | IllegalArgumentException e) {
                return unauthorized(exchange);
            }
        };
    }

    private Mono<Void> unauthorized(ServerWebExchange exchange) {
        exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
        return exchange.getResponse().setComplete();   // stop here, don't call the chain
    }

    @Data
    public static class Config {
        private boolean enabled;
    }
}

setComplete() ends the response, and because chain.filter is never called, the request never reaches discovery or the service. In the success path the service receives the mutated exchange, so this is the same "exchange is a wrapper you can replace" idea from section 3.

YAML: protected and public routes

routes:
  - id: auth-service              # login / signup: public, no Authentication filter
    uri: lb://AUTH-SERVICE
    predicates:
      - Path=/api/v1/auth/**
    filters:
      - StripPrefix=2

  - id: order-service             # protected
    uri: lb://ORDER-SERVICE
    predicates:
      - Path=/api/v1/orders/**
    filters:
      - StripPrefix=2
      - name: CustomLogging
        args:
          message: "Custom Logging Filter for Order Service"
      - name: Authentication      # class name minus "GatewayFilterFactory"
        args:
          enabled: true           # binds to Config.enabled

Route filters are ordered by their position in the list (1, 2, 3). Here Authentication is order 3. If you want unauthenticated requests rejected before anything else runs, list it first.

Shared secret vs public key. With Keys.hmacShaKeyFor(secret) (HS256) the same secret signs and verifies, so every service holding it could also forge tokens. With RS256 the auth service signs with a private key it never shares, and the gateway and services only hold the public key to verify. That matches your "validate using public key" flow. In jjwt it becomes Jwts.parser().verifyWith(publicKey) with an RSA PublicKey. Whichever you use, keep the key out of source code (your ${JWT_SECRET_KEY} approach is right) and use a key of at least 256 bits for HS256.

11. Config Server (properties from a Git repo)

Why we need it

Without it, every microservice keeps its own application.yml inside its jar. With many services that gets painful: the same value (the Eureka URL, say) is copied into every service, changing a property means rebuilding and redeploying that service, and secrets and per-environment (dev/prod) values are scattered everywhere.

A Config Server is one central service that reads the properties from a Git repository and serves them over HTTP. Services fetch their configuration from it at start-up. You get one place to edit, Git history and review for every change, and profile-based values (dev, prod) for free.

Revoke the token you pasted. The GitHub personal access token (PAT) you shared in this chat is now exposed. Revoke it in GitHub (Settings, Developer settings, Personal access tokens) and create a new one with read-only access to the config repo only. Never put a token in application.yml or commit it: in the file below it is read from the environment variable GIT_PAT. I used a placeholder in this page.

Step 1: set up the Config Server

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-config-server</artifactId>
</dependency>
@SpringBootApplication
@EnableConfigServer          // turns this app into a config server (exposes the config endpoints)
public class ConfigServerApplication { ... }

If it also registers with Eureka (your YAML has a eureka block), it needs the Eureka client dependency too.

Step 2: create the Git repo and token

Create a repo (yours is config-server) holding one file per service, plus one shared file:

config-server (git repo, branch main)
├── application.yaml        ← global: applies to EVERY service (e.g. Eureka URL)
├── api-gateway.yml         ← only for the app named "api-gateway"
├── api-gateway-dev.yml     ← only for api-gateway when profile "dev" is active
├── order-service.yml
└── inventory-service.yml

The file name must be the service's spring.application.name, optionally followed by -profile. The PAT lets the Config Server read the repo (needed for a private repo).

Step 4: what a client service needs

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-config</artifactId>
</dependency>

The dependency alone isn't enough: the client must also be told where the server is and who it is. Its local application.yml shrinks to just this:

spring:
  application:
    name: api-gateway        # must match the file name in the repo (api-gateway.yml)
  config:
    import: "optional:configserver:http://localhost:8888"
  profiles:
    active: dev              # optional, picks api-gateway-dev.yml too

optional: lets the app start even if the Config Server is down (without it, start-up fails). On Spring Boot 3.3+ this spring.config.import style is the standard way, and no bootstrap.yml is needed (that was the older approach). Use the Spring Cloud release that matches your Boot version (Boot 3.3.x pairs with Spring Cloud 2023.0.x; check the compatibility table on the Spring Cloud site).

Why a local file is still needed, even though properties come from Git

Every service must keep a tiny local application.yml (or .properties) containing at least its application name and the Config Server address. Two reasons:

  • It is needed to fetch the config. The service can't read anything from the Config Server until it knows who it is (spring.application.name, which picks api-gateway.yml in the repo) and where the server is (spring.config.import). Those two values can't come from the place they are needed to reach.
  • The same name is the Eureka registration name. After the properties are loaded, the service registers itself in Eureka under spring.application.name (shown as ORDER-SERVICE). That is the name the gateway uses in lb://ORDER-SERVICE. So one property does two jobs: the key for config lookup and the identity in Eureka.
Local file read first: name, config import, profile
Fetch from Config Server using that nameRemote properties arrive: routes, shared Eureka URL, etc.
Service registers in Eureka as spring.application.name using the Eureka URL it just received
# order-service: local application.yml (the only file inside the jar)
spring:
  application:
    name: order-service
  config:
    import: "optional:configserver:http://localhost:8888"

The same thing as a .properties file (local application.properties of inventory-service):

spring.application.name=inventory-service
spring.config.import=optional:configserver:http://localhost:8888

These two lines must exist locally in the service's own application.yml / application.properties. Everything else can live in the Git repo.

If the name is missing, Spring uses application when asking the Config Server (so you only get the global application.yaml) and the service registers in Eureka as UNKNOWN. Both look like "it works but nothing is right", so set the name first.

Correction: Eureka does not (by default) help find the Config Server

Your flow says all services are registered in Eureka and each one calls the Config Server. The second part is right, but in the setup above the client finds the Config Server by the fixed address in spring.config.import, not through Eureka. There is a chicken-and-egg problem: the Eureka URL itself lives in the Config Server's application.yaml, so a service can't use Eureka to find the Config Server before it has fetched the Eureka URL.

Option A: fixed URL (what you have)

Simple. Each service knows localhost:8888 (or an environment variable for other environments). The Config Server doesn't strictly need to register in Eureka.

Option B: discovery first

Services look up config-server in Eureka (spring.cloud.config.discovery.enabled=true). For this to work every service must keep the Eureka URL in its own local file, not in the Config Server's.

Things that commonly go wrong

  • Wrong or mismatched file name: if spring.application.name doesn't match xyz.yml, the server still answers successfully, but only with the global application.yaml. No error, just missing values.
  • Config is loaded at start-up. Editing the Git file doesn't change a running service; restart it (or use refresh support) to pick it up.
  • Start order: Eureka, then Config Server, then the other services.
  • Secrets: keep real secrets out of Git. Use placeholders like ${JWT_SECRET_KEY}, as you did, and set the variable on the service.
  • Environment variables and command-line arguments override values coming from the Config Server, and by default the Config Server's values override the service's local application.yml.

12. Refresh scope: change properties without restarting

The problem

A service reads its properties once, at start-up. If you change a value in the Git repo, the Config Server will serve the new value, but the running service still holds the old one. Without a solution you must restart that microservice after every change.

The solution in two parts

PartJob
1. Actuator refresh endpointA POST endpoint that tells the service: "fetch your properties again now".
2. @RefreshScope on beansMarks beans that must be rebuilt with the new values after a refresh.

Part 1: expose the refresh endpoint

The service needs the actuator dependency (spring-boot-starter-actuator). Then expose the endpoint:

management:
  endpoints:
    web:
      exposure:
        include: refresh        # only the refresh endpoint
        # include: "*"          # all actuator endpoints (quotes are needed in YAML)

"*" exposes everything (env, beans, heapdump and so on). That is fine while learning, but in real setups expose only what you need and secure the actuator endpoints, since anyone who can call refresh can make your services reload configuration. A handy trick: put this block in the global application.yaml in the Git repo, and every service gets it.

Part 2: mark beans with @RefreshScope

@RefreshScope
@Service
public class InventoryService {

    @Value("${variable.name:default}")
    private String variableName;     // re-read after a refresh

    ...
}

It works on any bean (@Service, @Component, @RestController, a @Bean method). A bean without it is created once, keeps the values it got at creation, and ignores the refresh.

Use it deliberately. Not every bean needs dynamic properties. Put @RefreshScope only on beans whose values really must change at runtime (feature flags, limits, messages, URLs). Each refresh destroys and recreates those beans, which costs work and loses any state kept inside them, so avoid it on heavy or stateful beans (connection pools, caches).

Triggering it

After you push the change to the Git repo, send a POST (not GET) to the service's refresh endpoint:

POST http://localhost:9010/inventory/actuator/refresh

The URL is: service port (9010) + the service's context path (/inventory) + /actuator/refresh. No context path means just :9010/actuator/refresh.

ResponseMeaning
[]Nothing changed since the last load.
["config.client.version", "variable.name"]These property keys changed. variable.name is your edited value. config.client.version holds the Git commit id the config came from, so it changes whenever a new commit is picked up.

What happens behind the scenes

1. You commit and push the new value to the Git repo
2. You POST /actuator/refresh to the service
3. The service asks the Config Server againThe Config Server pulls the latest commit from Git, so it needs no restart. The service compares the result with its old Environment.
4. The service replies with the list of changed keys
5. All @RefreshScope beans are thrown away (their cache is cleared)Beans without @RefreshScope are untouched.
6. On the next call, a fresh bean is created with the new values

Why it works: proxies

Other beans can't simply be re-injected with a new object while the app is running, so @RefreshScope uses a proxy. What gets injected into other beans (for example a controller using InventoryService) is not the real object but a stand-in with the same type. The proxy forwards each method call to the real bean, which is kept in a cache.

Controller ──► Proxy of InventoryService  (same proxy for the whole app lifetime)
                    │ forwards calls to
                    ▼
               real InventoryService   (variableName = "old")

after refresh: the real bean is discarded
Controller ──► same Proxy ──► NEW real InventoryService (variableName = "new")
                               (created lazily on the next call)

So the controller never needs to be touched: it keeps the same proxy, and the proxy quietly points to a fresh bean with fresh properties. The new bean is created lazily, at the first call after the refresh. Because the proxy is generated as a subclass, the class shouldn't be final.

Limits to know

  • Per instance: the POST refreshes only the instance you call. With three instances of inventory-service, you must call all three. Spring Cloud Bus (with RabbitMQ or Kafka) can broadcast one refresh to every instance.
  • Startup-only properties: things used while the app starts (server.port, a connection pool size) won't change just by refreshing.
  • Bound properties: classes using @ConfigurationProperties are re-bound on refresh even without @RefreshScope.
  • Gateway: routes defined in properties are reloaded after a refresh, because the gateway listens for the refresh event and rebuilds its routes.
  • Nothing changes? Check that the change was committed and pushed to the branch the Config Server reads (main), and that the key is in a file that applies to this service.

13. Distributed tracing: Micrometer + Zipkin

Why we need it

One user request now crosses several services (gateway, order-service, inventory-service). When it is slow or fails, each service's own log only shows its small part. Tracing follows one request across all services and answers: which services did it pass through, how long did it spend in each, and where did it fail. This is part of observability.

TermMeaning
Trace (traceId)The whole journey of one request. One traceId, the same in every service the request touches.
Span (spanId)One unit of work inside the trace: a service handling the request, or a service making an outgoing call. Has a start time and a duration.
Parent span idWhich span caused this one. It links the spans into a tree. The first span has no parent.
SamplingDeciding whether a request is recorded at all (tracing has a cost).

One traceId, many spanIds. Micrometer creates and passes these ids; Zipkin collects the finished spans and draws them.

Step 1: run Zipkin

docker run -p 9411:9411 openzipkin/zipkin:latest

Open http://localhost:9411/zipkin/ (http://127.0.0.1:9411/ also works). It is empty until your services send traces, which is why you see "Search Traces" first. By default this image keeps data in memory, so traces disappear when the container restarts.

Step 2: add the dependencies

<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-actuator</artifactId></dependency>
<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-observation</artifactId></dependency>
<dependency><groupId>io.micrometer</groupId><artifactId>micrometer-tracing-bridge-brave</artifactId></dependency>
<dependency><groupId>io.zipkin.reporter2</groupId><artifactId>zipkin-reporter-brave</artifactId></dependency>
<!-- only in services that call others with OpenFeign -->
<dependency><groupId>io.github.openfeign</groupId><artifactId>feign-micrometer</artifactId></dependency>

Add them to the api-gateway and every microservice in the request path. Not to the Eureka server or Config Server: they are infrastructure and don't take part in business requests, so tracing them would only add noise.

DependencyWhat it does
spring-boot-starter-actuatorBrings Micrometer and the Spring Boot auto-configuration that switches tracing on and reads the management.tracing.* properties. Required.
micrometer-observationThe Observation API: code (Spring's HTTP server and client, Feign) marks "something started / ended" once, and handlers turn that into metrics or spans. Spring already instruments incoming and outgoing HTTP calls with it.
micrometer-tracing-bridge-braveMicrometer Tracing is a facade; this bridge plugs in Brave (the tracer from the Zipkin project). Brave generates the trace and span ids, remembers the current span, and writes/reads the propagation headers.
zipkin-reporter-braveThe reporter: takes finished spans and sends them to the Zipkin server over HTTP.
feign-micrometerObservation support for OpenFeign clients. Needed only where Feign is used.

Step 3: properties

management.tracing.sampling.probability=1.0
management.zipkin.tracing.endpoint=http://localhost:9411/api/v2/spans
logging.pattern.level=%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]
eureka.instance.prefer-ip-address=true
  • Sampling probability. 1.0 traces every request, 0.1 traces 10%. Spring Boot's default is 0.1, so with no setting you'd see only about one request in ten. Tracing costs CPU (creating spans), memory and network (sending them), so use 1.0 while learning and a lower value in production. The decision is made once, at the first service (the gateway), and travels with the request, so a trace is either recorded in all services or in none.
  • Zipkin address. You wrote spring.zipkin.base-url=http://localhost:9411. As far as I know that property belonged to Spring Cloud Sleuth (Boot 2) and Boot 3 ignores it. In Boot 3 it is management.zipkin.tracing.endpoint, whose default is already http://localhost:9411/api/v2/spans, which is why your traces work with Zipkin on the same machine. Set it explicitly once Zipkin lives elsewhere. The article you followed doesn't set it at all.
  • Log pattern. Puts [service, traceId, spanId] in every log line, so you can search the logs of all services for one traceId. Micrometer stores the ids in the logging MDC. (The article says Sleuth does this; on Boot 3 it is Micrometer Tracing. Newer Boot 3 versions may add the ids to logs automatically.)
  • Shared properties. Since you have a Config Server, put these in the global application.yaml in the Git repo and every service receives them. Sampling is read at start-up, so restart the services after changing it.

Step 4: the beans (this is where tracing silently breaks)

A trace continues across services only if the outgoing HTTP call carries the trace headers. Spring adds them through an instrumentation hook, and that hook is attached only to clients built the Spring way:

// RestTemplate: must be built from RestTemplateBuilder
@Bean
public RestTemplate restTemplate(RestTemplateBuilder builder) {
    return builder.build();           // NOT new RestTemplate()
}

// OpenFeign: register the Micrometer capability (from the article)
@Bean
public Capability capability(final MeterRegistry registry) {
    return new MicrometerCapability(registry);
}

The same rule applies to RestClient and WebClient: inject and use their auto-configured Builder. With new RestTemplate() nothing adds the headers, so the next service doesn't know it is part of a trace and starts a new trace. The article warns that, with Feign and no such bean, a new traceId appears for every span. You then see disconnected one-service traces instead of one tree.

The article's Feign bean uses MicrometerCapability with a MeterRegistry. Newer feign-micrometer versions also have MicrometerObservationCapability with an ObservationRegistry. I haven't checked which one your versions need; if your Feign calls show up as separate traces, try the observation-based one.

Step 5: why eureka.instance.prefer-ip-address=true

A service registers itself in Eureka with an address, and the gateway and other services use that address to call it (lb://ORDER-SERVICE becomes host:port). By default Eureka registers the machine's hostname, like Victus.mshome.net in your screenshots. A caller then has to be able to resolve that name through DNS. That works on one machine, but often fails between Docker containers, other machines or other networks. With prefer-ip-address=true the service registers its IP address instead, so callers connect directly and no name lookup is needed. Put it in the services' config (for example the shared application.yaml). On laptops the IP chosen can be a virtual adapter (Docker, WSL), which only the same machine can reach, so check what is registered in the Eureka dashboard.

The odd single-span trace is Eureka's heartbeat

This is not a user request. It is order-service renewing its lease with the Eureka server (a PUT to /eureka/apps/<APP>/<instance-id>), which every Eureka client does about every 30 seconds by default. The Eureka client's HTTP call is instrumented too, so each heartbeat becomes its own tiny trace. The instance id is hostname:app-name:port, so this shows order-service on port 9020. Ignore these: real request traces have several spans and several services. Use the Zipkin search (service name, span name) to filter them out.

How it works internally

Client
  │  POST /api/v1/orders/...                      (no trace headers yet)
  ▼
api-gateway     creates traceId + root spanId, makes the sampling decision
  │  outgoing call carries:  traceparent: 00-<traceId>-<gateway client spanId>-01
  ▼
order-service   reads the header, KEEPS the traceId, creates a new span (parent = caller's span)
  │  its outgoing call (Feign/RestTemplate) adds the same header with its own span id
  ▼
inventory-service   same again: same traceId, another span

each service  ──(async, batched)──►  Zipkin   : "here are my finished spans"
Zipkin groups spans by traceId and links them with parent span ids into one tree
  1. A request arrives. Spring's HTTP server instrumentation starts an observation. The tracing handler (micrometer-tracing with Brave) looks for trace headers. If there are none (the gateway, for a client request) it generates a new random traceId and a root spanId (in your screenshots the root span id is the last 16 characters of the trace id, a Brave convention) and decides whether this trace is sampled.
  2. The current span is remembered for the thread handling the request, and its ids are placed in the logging MDC (hence the ids in the log lines).
  3. An outgoing call is made. The instrumented client (built from the builder, or Feign with the capability) starts a child span and adds the trace headers to the outgoing request. By default Spring Boot 3 uses the W3C traceparent header (traceId, parent span id, and a sampled flag); B3 headers can be configured instead. This is the only thing passed between services: ids, not span data.
  4. The next service extracts the headers. It continues the same traceId, creates its own server span whose parent is the caller's span, and respects the sampled flag.
  5. Spans are finished and reported. When a span ends, Brave hands it to the Zipkin reporter, which queues it in memory and sends batches to Zipkin (POST /api/v2/spans) on a background thread, so the request isn't delayed by network calls to Zipkin. Each service reports its own spans independently.
  6. Zipkin stitches the picture. It stores the spans, groups them by traceId, builds the tree from parent ids, and derives the Dependencies graph from which service called which.

Is there a heartbeat to Zipkin? No. Services push finished spans in batches; Zipkin doesn't poll them. The heartbeat in your screenshot belongs to Eureka. A service only appears in Zipkin when it has produced traces.

If nothing shows up

  • Missing actuator or tracing dependency in that service, or Zipkin isn't running or reachable.
  • Sampling too low (default 0.1): set 1.0 while testing.
  • Trace splits into separate traces: an HTTP client was created without the builder, or the Feign capability bean is missing.
  • Zipkin restarted: in-memory storage lost the old traces. For real use, configure a storage backend (for example Elasticsearch).
